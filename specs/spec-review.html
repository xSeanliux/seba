Tutor — Design Spec Review

1 · What this is

A long-term personal tutor that runs in the terminal. You converse with it daily; it teaches through guided dialogue and practice questions. Unlike chat "learning modes", it owns a curriculum (concept graph synthesized from a textbook ToC + web research) and a longitudinal learner state (known / shaky / due), both plain text in git. Session 40 provably knows what happened in session 1.

First two subjects, built simultaneously to force honest abstraction: Probability (concept-heavy, teach-heavy) and Italian (item-heavy, review-heavy).

Out of scope: learning feed, e-ink, Telegram, web UI, full PDF ingestion. Future satellites attach at the plain-text state seam.

2 · Core principle: the seam

Split by what must be deterministic vs. what benefits from model judgment:

  • Code owns: state storage, schema validation, FSRS scheduling, graph ops, agenda construction, applying updates.
  • LLM owns: syllabus drafting, teaching dialogue, grading free-form answers, distilling sessions.

The boundary is typed in both directions:

  1. Agenda (code → LLM): what this session covers, scheduler-computed.
  2. Outcome tools (LLM → code): the tutor records what happens during the session via validated tool calls — grade_review, mint_item, update_concept, end_session. Each call schema-checked the moment it's made (bad args → immediate in-flow retry); grades land while the exchange is fresh; a crash loses nothing already recorded.

A transcript-level extraction pass survives only as crash recovery (tutor extract) for sessions that die before end_session.

The LLM never edits state files — tools are code functions applying validated updates. Code never generates prose. Every module is testable without an LLM by injecting synthetic artifacts at this seam.

4 · Data model

Syllabus — syllabus.yaml

concepts:
  - id: conditional-expectation-as-rv
    name: "Conditional expectation as a random variable"
    prereqs: [conditional-probability, random-variables]
    sources: ["blitzstein/ch09.md#9.2"]
    status: unseen            # unseen | in-progress | done  (v0)
    est_sessions: 2

Prereqs must form a DAG (cycle → hard error naming the cycle). frontier() = concepts whose prereqs are all done.

Items — items.jsonl

{"id":"it-041","concept":"law-of-total-probability","type":"recall",
 "front":"State the law of total probability","back":"P(A) = Σ P(A|Bᵢ)P(Bᵢ) …",
 "fsrs":{"stability":4.2,"difficulty":6.1,"due":"2026-07-05","state":"review"},
 "created":"2026-06-28","suspended":false}

type ∈ recall · apply · cloze · produce · recognize. The fsrs block is owned by py-fsrs; other modules read only due.

Agenda (code → LLM)

class Agenda(BaseModel):
    goal: str; subject: str; session_number: int
    briefing: str                       # scheduler-assembled memory summary
    review_items: list[ReviewItem]      # FSRS-due, capped per subject preset
    teach_concept: TeachConcept | None  # + source_excerpts pulled from files
    practice_quota: int
    pace_hint: Literal["push-harder","steady","step-back"]  # from recent success rate

Outcome tools (LLM → code, validated per call)

grade_review(id, grade: again|hard|good|easy, note?)   # right after each review resolves
mint_item(concept, type, front, back)                   # worth retaining a month from now
update_concept(id, status_change?: started|completed, note?)
end_session(summary, next_session_hint)                 # exactly once, at close

Handlers reject unknown ids and over-cap mints (10/session) with an explanation the model sees and corrects in-flow. Accepted calls accumulate in a SessionRecord, applied by the store at save time and serialized to NNN.outcomes.yaml as the audit trail.

Deterministic gates — code checkpoints at the boundaries, dialogue free in the middle: (1) session-end gate: end_session//done rejected while agenda reviews remain ungraded — handler returns missing ids, model must grade or mark skipped (FSRS untouched, stays due) before close is accepted; (2) save-time invariants: exactly one end_session, grades map to agenda items, statuses move only along legal edges — violation → saved INCOMPLETE, state never corrupted.

7 · Session lifecycle

tutor
 └─ load goal → build agenda → briefing card
 └─ run_session:
     1. tutor opens with continuity ("last time…"), poses first due review
     2. per review: you answer → corrective feedback, misconception named
          → grade_review(...) recorded silently → next
     3. reviews done → teach segment: worked example → faded → solo practice
          attempts drive update_concept(...) / mint_item(...)
     4. tangents anytime; tutor may fetch_source(ref)
     5. /done (or budget) → verbal recap → end_session(summary, hint)
 └─ scheduler finalizes FSRS state; syllabus statuses applied
 └─ store.save_session(...)           ← one git commit
 └─ receipt: "4 reviewed · 2 minted · conditional-expectation → in-progress"

Failure handling: tool calls are accepted during the session, so a crash loses nothing already recorded — partials saved with an INCOMPLETE marker; tutor extract <goal> <n> backfills anything after the last accepted call. A session's learning is never lost to a parse error.

8 · Prompts (contracts)

  • system_base.md — subject-agnostic; all subject character lives in overlays. Long-term tutor mid-relationship; briefing is your memory. Pedagogy: worked example → faded scaffolding → independent practice; ~85% target success; honor pace_hint; name misconceptions when correcting; weave reviews in early, get a real attempt, call grade_review as each resolves; tangents allowed (record durable bits via tools); never dump an answer one hint away; recap aloud, then end_session.
  • subjects/probability/overlay.md — Unicode math (𝔼[X|Y], σ-algebra), LaTeX fences only for long derivations; practice = compute / prove-sketch / counterexample; statements and intuitions.
  • subjects/italian/overlay.md — increasing fraction of session in Italian by level; production over recognition; correct by recasting, then drill the pattern.
  • Tool descriptions carry contracts — grading rubric (wrong → again; correct-with-hints → hard; correct → good; instant → easy) lives in grade_review; "worth retaining in a month" lives in mint_item.
  • New subjects need zero code: a subject = profile.yaml (scheduling knobs) + overlay.md, drafted from templates by new-goal when missing, edited in $EDITOR.

9 · UX — what the user does

Once per goal (~30 min): tutor new-goal probability --toc blitzstein-toc.md → skim/edit the drafted syllabus in $EDITOR. The only real setup — and it's your curriculum.

Every time: type tutor, pick goal, talk. Quit whenever — extraction and save are automatic. Zero bookkeeping: no self-grading, no card authoring, no marking complete. The conversation is the interface.

Sometimes: tutor status; approve syllabus revision diffs; edit YAML when an estimate feels wrong; drop in a new source file.

9a · Context budget

The scheduler is the context firewall: the model sees a selection, never the state. Enforced in build_agenda:

  • Items: only FSRS-due, capped per profile (6 / 20). The thousands-card items.jsonl never enters context.
  • Syllabus: briefing names counts + frontier (≤10 concept names), never the full graph.
  • Notes: notes.md structured per-concept; briefing includes only this session's scope (review items' concepts, teach concept + direct prereqs), ≤3 newest notes each, ~1k-token budget, oldest truncated first.
  • Sources: section-granularity excerpts, ~4k-token budget; over → keep primary, drop rest, note it.
  • History: last session's hint only; transcripts never fed forward.
  • Consolidation (v1): tutor gc — a concept's notes exceed 5 → cheap-model pass distills them into one.
Net: session context ≈ system prompt (~2k) + agenda (~1–5k) + live dialogue — independent of months of history or thousands of items.

10 · Build order

Milestone v0 — the loop

  1. models.py + M1 store + M3 syllabus, with tests (no LLM)
  2. M2 scheduler + 30-day simulation test (no LLM)
  3. M4 session: dialogue + outcome tools + recovery, fixture-tested
  4. M5 synthesis (single-call, incl. profile drafting) + M6 REPL + CLI
  5. Dogfood gate: both real goals, 3 real sessions each across ≥3 days. Success = session N+1's briefing correctly reflects session N.

Steps 1–2 and 3 parallelize across agents once models.py is merged; models.py is a single owned artifact, first.

Milestone v1 — by observed pain

Concept ladder · tutor drill <goal> — review-only rapid-fire mode (the "dojo"; same agenda machinery, terse overlay — for when Italian's due queue outgrows conversational weaving) · agentic synthesis with web search · pace model from logs · notes consolidation (tutor gc) · tutor extract polish · TUI upgrade (textual).

11 · Testing & risks

Testing: seam tests dominate (synthetic state → agenda; synthetic outcomes → state; zero API cost). Fixture transcripts for extraction in a separate pytest -m llm tier. 30-day FSRS sim doubles as the BKT-sim spike. Dogfooding is the real test.

Config defaults: dialogue claude-sonnet-5, extraction claude-haiku-4-5 (both env-overridable); Python ≥3.12 + uv; FSRS defaults, retention 0.9.
